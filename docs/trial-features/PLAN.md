# trial-features implementation plan

Branch `trial-features`, cut from `3.0` on 2026-11-20 (so the Wazuh 5.0
adapter is included). Nothing here is released; the branch may be reconciled
into 3.0.0 later. Features are built in the order the owner chose: **6, 5, 3,
2, 1** (see [RECOMMENDATIONS.md](RECOMMENDATIONS.md)). Multi-tenancy (4) is
dropped. Reuse-versus-build decisions come from
[REUSE-STUDY.md](REUSE-STUDY.md) (verified against a live 4.14.10 stack and
5.0.0 sources); its short version is the table below.

Check a box only when the step is implemented, unit-tested in the dev image,
and (where it has UI) exercised by a Playwright spec against the Docker stack.

## What is reused from Wazuh instead of rebuilt

| Need | Wazuh 4.14.10 | Wazuh 5.0 | Our approach |
|---|---|---|---|
| Delivery channels (Slack, Teams, webhook, email, SNS) | Indexer Notifications plugin has channels but no "send" REST API | Same (OpenSearch 3.6 fork, send API only arrives in 3.10); four disabled placeholder channels; private hosts denied by default | **Reuse channels** as a transport: our dispatcher sends through an inline Alerting `_execute` with the channel as action target (verified 0.4–1.4 s, nothing persisted). Our own outbox, retries and dead-letter stay because Alerting monitors cannot do them. A direct HMAC webhook is kept for signed, private-LAN or sub-minute receivers. |
| Email | Notifications `smtp_account` + email channel (text only, no attachments) | Same | **Reuse**; no SMTP client in this plan. |
| Threat-intel lookups | None native (VirusTotal/Maltiverse integrator scripts write *sibling* alerts; CDB IOC lists change the rule id) | Content Manager syncs the CTI IoC catalog into `wazuh-threatintel-enrichments*`; the engine stamps `wazuh.threat.enrichments[]` on findings; CTI Explorer is a local reader of that index with no lookup API | **Ingest** every native verdict that already exists (4.x sibling alerts, CDB rule ids, 5.0 engine enrichments) and add a built-in `wazuh_cti_local` source on 5.0 that queries the local index. **Build** cached on-demand lookups for AbuseIPDB / MISP / generic HTTP and per-case indicator aggregation, which nothing native does. Never call the Wazuh CTI API. |
| GeoIP | Indexer pipeline `GeoLocation.*` (2019 DB, last IP wins) | Engine ECS `<entity>.geo.*` / `.as.*` | **Ingest** as hints with a caveat; never build a lookup. |
| Asset context | `agent.{id,name,ip}` on alerts; groups only via the server API; 13 `wazuh-states-inventory-*` + `wazuh-states-vulnerabilities-*` indices (empty until agents enrol) | `wazuh.agent.groups` on every finding; `wazuh-states-*` bare indices incl. SCA | **Ingest** groups (5.0 natively, 4.x via the optional `wazuhCore` API client in the sync job), **ingest** states indices for asset chips (OS, ports, critical CVEs, SCA) with deep links to IT Hygiene / Vulnerability Detection. **Build** only the criticality matcher (name/glob/group → criticality + tags). |
| CSV export / scheduled reports | OpenSearch Reporting: saved-search CSV works but needs `reports_full_access`, corrupts under concurrency, and its scheduler delivers nothing | Fork emails a link to an unrendered instance | **Build** our own CSV routes and a small scheduler delivering Markdown summaries through our channels. Optionally provision index patterns + saved searches so Discover/Reporting work on our indices. |
| PDF | Wazuh module PDFs (private pdfmake), Reporting dashboard PDFs (browser-side) | Module PDFs removed | **Build** printable HTML + Markdown; "PDF" is the browser print path. |
| Case management | None | `wazuh.case.*` on one finding (title, description, tags, status, severity, priority, TLP, comments); no id, grouping, assignee, tasks, timeline, attachments, SLA; written via `_security_analytics/findings/_update` with no shipped write role | **Build** ours (already the product). Read-only projection of `wazuh.case.*` onto 5.0 records; never write back. |
| SLA breach detection | Alerting query/bucket monitors can detect, but degrade silently above 50 matches, need analyst role mappings, cannot reassign or raise severity | Same | **Build** our scanner; the Alerting mirror idea is dropped. |
| Scheduling / leader election | job-scheduler is a Java SPI; its REST lock API works but is undocumented for `kibanaserver` | Same | **Build** a small lease on our meta index. |
| Active response | Integrator scripts | Incident Response app, `wazuh-active-responses` | Out of scope (not selected). |

## Decisions taken on the study's open questions (2026-11-20; owner may override)

- Q1 Email: reuse the Notifications email channel; no SMTP client.
- Q2 Service identity: `install.sh` creates the least-privilege role `wazuh_alert_manager_notify` (alerting `monitor/execute`, notifications `configs/get` + `feature/publish`, read on the outbox index; verified live on 4.14.10) and maps it to the dashboard user (opt-out flag `--skip-notification-role`); the reserved `alerting_full_access` role is not used. The dispatcher records a 403 as `last_error` when the grant is missing.
- Q3 `wazuhCore`: accepted as an *optional* plugin dependency, used only from the sync job and only when present; everything degrades to name/glob/label matching without it.
- Q4 Read grants: `install.sh` adds read on `wazuh-states-*` and (5.0) `wazuh-threatintel-enrichments*` to the plugin role (opt-out flag `--skip-native-read-role`); the UI degrades to "no access" chips.
- Q5 Alerting breach mirror: dropped.
- Q6 5.0 native cases: read-only projection of `wazuh.case.*` (step 2.6); no write-back.
- Q7 Disposition → detection silencing: not in this plan; recorded in RECOMMENDATIONS.md as a future item.
- Q8 Discover/Reporting integration: included as the last step of phase 5 (5.6).
- Q9 Private receivers: `WAZUH_ALERT_MANAGER_EGRESS_ALLOWED_HOSTS` is the documented escape hatch for direct webhooks and enrichment sources; the 5.0 `host_deny_list` override is documented for indexer channels.
- Q10 Lease: keep `lease.ts`.
- Q11 5.0 verification: `wazuh/wazuh-dashboard:5.0.0-rc2` images exist on Docker Hub; a 5.0 stack is brought up for a verification pass at the end of phase 6 and again in phase 7.
- Q12 4.x GeoLocation: shown only when present, labelled as an indexer-pipeline hint with the database caveat.
